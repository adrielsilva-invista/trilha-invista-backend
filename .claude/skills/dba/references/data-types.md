# Seleção de Tipos de Dados (PostgreSQL)

A heurística sênior, por coluna: **semântica → range/precisão/cardinalidade →
padrão de consulta → tipo correto mais estreito.** Correção primeiro; só depois
otimize a largura da linha. Este arquivo é o catálogo profundo; a tabela do
SKILL.md é a versão rápida.

## Numéricos

### Inteiros
- `smallint` (2 bytes, ±32K), `integer` (4 bytes, ±2.1B), `bigint`
  (8 bytes, ±9.2×10¹⁸).
- Escolha pelo domínio real do valor. Idade → `smallint`. Contagens de linhas, IDs
  em escala → `bigint`. Contadores gerais → `integer`.
- **PKs surrogate → `bigint`.** Os 4 bytes extras são seguro barato; ficar sem PKs
  `integer` em produção é um outage genuíno e doloroso que atinge tabelas movimentadas
  (ou tabelas com muitos deletes/reinserts) mais cedo do que as pessoas esperam.

### Identity (auto-incremento)
- Use `GENERATED ALWAYS AS IDENTITY` (padrão SQL, Postgres 10+):
  ```sql
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
  ```
- **Evite `serial`/`bigserial`.** São açúcar sintático que cria uma sequence com
  posse frágil, vaza footguns de `INSERT` na coluna de identidade, e concede
  privilégios default estranhos. `GENERATED ALWAYS` inclusive bloqueia inserts
  manuais na coluna (use `GENERATED BY DEFAULT` apenas se você precisa fornecer
  valores, ex. migração de dados).

### numeric / decimal (exato)
- `numeric(precision, scale)` — precisão arbitrária, exato. `numeric` e `decimal`
  são idênticos no Postgres.
- **Este é o tipo para dinheiro e qualquer coisa onde erros de arredondamento são
  inaceitáveis.** `numeric(12,2)` guarda até 9.999.999.999,99.
- Mais lento que inteiros/floats (matemática em software, não hardware), então não
  use para medidas aproximadas de alto volume.
- `numeric` sem restrição (sem precisão) é permitido mas fixe precisão/escala para
  dinheiro para que dados ruins não entrem sorrateiramente.

### Ponto flutuante (aproximado)
- `real` (4 bytes, ~6 dígitos), `double precision` (8 bytes, ~15 dígitos).
- **Escolha correta para medidas físicas/científicas** onde valores são
  inerentemente aproximados: leituras de sensor, coordenadas, pesos, razões,
  percentuais usados em analytics.
- **Errado para dinheiro.** `0.1 + 0.2 <> 0.3` em float binário. Se você ver
  `float`/`double` numa coluna de moeda em review, sinalize como bug.

### O tipo `money` — evite
- Formatação dependente de locale, escala fixa atrelada a `lc_monetary`, matemática
  desajeitada. Use `numeric` ou unidades monetárias inteiras.

### Padrão de centavos-inteiros
- Para dinheiro exato de alta vazão (ledgers, processadores de pagamento), armazene
  a menor unidade da moeda como `bigint` (ex. centavos) mais uma coluna
  `currency char(3)`. Rápido, exato e inequívoco — ao custo de dividir por 100 na
  camada de apresentação. Documente a escala.

## Texto

### text vs varchar(n) vs char(n)
- **`text` é o default.** No PostgreSQL, `text`, `varchar` e `varchar(n)` têm
  **armazenamento e performance idênticos**; `varchar(n)` só adiciona uma checagem
  de tamanho. Não há ganho de velocidade em `varchar(255)` — esse número é um
  hábito da era MySQL, sem significado no Postgres.
- Use `varchar(n)` (ou `text` + um `CHECK`) **apenas quando o limite for uma regra
  de negócio/interoperabilidade real** (um campo bancário de exatamente 11 chars,
  uma API externa que rejeita >100). Prefira um `CHECK` nomeado porque a intenção
  fica explícita e o limite é fácil de mudar:
  ```sql
  slug text NOT NULL CONSTRAINT ck_articles_slug_len CHECK (char_length(slug) <= 80)
  ```
- **`char(n)` — evite.** Ele preenche com espaços em branco até o tamanho total,
  desperdiçando espaço e surpreendendo comparações (`'ab' = 'ab   '`). O raro uso
  legítimo é um código de fato fixo como moeda ISO `char(3)`; mesmo aí
  `text`/`varchar` é mais seguro.

### citext (case-insensitive)
- `citext` (da extensão `citext`) compara sem diferenciar maiúsculas/minúsculas,
  ideal para emails e usernames para que você não espalhe `lower()` por toda query
  e índice. Alternativa sem a extensão: mantenha `text` e crie um índice único
  funcional `ON users (lower(email))`. Escolha uma abordagem e aplique
  consistentemente.

## Temporais

### timestamptz — o default para pontos no tempo
- **Sempre prefira `timestamptz` (`timestamp with time zone`).** Ele armazena um
  instante absoluto (normalizado para UTC internamente) e converte para o fuso da
  sessão na leitura. Ele *não* armazena um fuso por linha — o nome é enganoso; ele
  armazena um momento inequívoco.
- `now()` / `current_timestamp` retornam `timestamptz`.

### timestamp (sem time zone) — a armadilha
- Armazena texto de relógio de parede sem offset. Dois clientes em fusos diferentes
  escrevem tempos absolutos conflitantes na mesma coluna e ninguém consegue
  distingui-los. Transições de horário de verão criam horas ambíguas/faltantes.
  **Só** use para um conceito genuinamente sem fuso (um "abertura da loja às 09:00"
  recorrente que significa local-onde-quer-que-seja), e mesmo assim documente
  claramente.

### date, time, interval
- `date` — data de calendário, sem hora (aniversários, datas de vencimento).
- `time` / `timetz` — hora do dia; `timetz` raramente é útil, evite.
- `interval` — uma duração. Use para durações com que você fará aritmética
  (`start_at + duration`), não um `integer` de segundos. Se for uma métrica
  simplesmente reportada, um int serve.

## Boolean
- `boolean` guarda `true`/`false`/`NULL`. Nunca modele uma flag como
  `char(1) 'Y'/'N'` ou `integer 0/1` — você perde a clareza do tipo e os benefícios
  de índice/planejador.
- Decida se `NULL` (desconhecido) é significativo; se não, `NOT NULL DEFAULT false`.

## UUID e estratégia de primary key

`bigint IDENTITY` vs `uuid` é uma bifurcação de design real:

- **`bigint IDENTITY`** — menor (8 vs 16 bytes), sequencial (ótima localidade de
  índice e comportamento de cache), legível por humanos. Desvantagens:
  adivinhável/enumerável, e IDs são únicos apenas dentro de um banco (chato para
  merges ou IDs gerados no cliente).
- **`uuid`** — globalmente único, gerável no cliente ou entre shards, não
  enumerável. Desvantagens: 16 bytes (índices/FKs maiores em todo lugar), e **UUIDv4
  aleatório destrói a localidade de insert** — inserts aleatórios se espalham pela
  B-tree, causando page splits e inchaço de índice em tabelas write-heavy.
- **Se você precisa de UUIDs, prefira UUIDv7 ordenado por tempo** (ou ULID) para
  que os valores sejam aproximadamente sequenciais e mantenham a localidade de
  índice. Armazene como `uuid` nativo, nunca como `text` (16 bytes vs 37, e `text`
  ordena/compara errado).

Recomendação default: `bigint IDENTITY` para PKs internas; `uuid` (v7) quando IDs
precisam ser gerados no cliente, expostos publicamente sem vazar contagens, ou
únicos entre sistemas. É comum manter uma PK `bigint` *e* uma coluna de referência
externa `uuid`.

## JSON / jsonb

- **Use `jsonb`, essencialmente nunca `json`.** `json` armazena texto cru (preserva
  espaço em branco/ordem de chaves/duplicatas) e não pode ser indexado de forma
  útil; `jsonb` é parseado, binário, deduplicado, e suporta índices GIN e operadores
  ricos.
- **Bons usos:** dados genuinamente variáveis ou esparsos — payloads de
  webhook/evento, campos customizados por tenant, respostas de APIs de terceiros,
  metadados flexíveis.
- **Anti-uso:** despejar dados estruturados em `jsonb` para pular a modelagem. Você
  abre mão de checagem de tipo, `NOT NULL`, foreign keys, defaults e índices baratos
  e direcionados, e toda query se enche de `->`/`->>` e casts.
- **Regra:** se você vai filtrar, juntar, ordenar ou agregar num campo, promova-o a
  uma coluna real. Mantenha o restante de fato variável numa coluna `jsonb`. Indexe
  caminhos quentes com índices de expressão (`(payload->>'status')`) ou GIN
  (`jsonb_path_ops`) conforme o padrão de acesso exigir.

## Enums vs tabelas de lookup vs CHECK

Três formas de restringir uma coluna a um conjunto fixo — tradeoffs diferentes:

- **Tabela de lookup + FK** (default para a maioria dos domínios):
  `order_statuses(id, code, label, ...)` com FK `orders.status_id`. Adicione/renomeie
  valores com DML comum, anexe metadados (labels, ordem de exibição, is_active), e
  faça join para relatórios. Um pouco mais verboso. **Melhor quando o conjunto pode
  crescer ou precisa de atributos.**
- **Tipo `enum`** — compacto, legível (`status order_status NOT NULL`), imposto pelo
  tipo. Mas **alterar enums é doloroso**: você pode `ADD VALUE` (não pode rodar
  dentro de alguns contextos de transação nas nuances pré-12) mas **remover ou
  reordenar um valor exige recriar o tipo** e reescrever colunas dependentes. Use
  apenas para conjuntos minúsculos e de fato estáveis (`weekday`, `card_brand`).
- **`CHECK (col IN (...))`** — zero objetos extras, ok para um conjunto pequeno e
  estável local a uma tabela. Mudar a lista é um `ALTER ... DROP/ADD CONSTRAINT`.
  Bom meio-termo; perde o vocabulário compartilhado e os benefícios de metadados de
  uma tabela de lookup.

Heurística: **estável + minúsculo + sem metadados → enum ou CHECK; qualquer coisa
que cresce ou precisa de labels/ordenação/flags → tabela de lookup.**

## Arrays
- `type[]` (ex. `text[]`, `int[]`) armazena uma lista ordenada em uma coluna.
- Aceitável para listas pequenas, limitadas e raramente consultadas onde a ordem
  importa e você não vai fazer join em elementos: tags numa linha, alguns telefones.
  Indexável por GIN para containment (`@>`).
- **Normalize numa tabela filha** no momento em que precisar impor FKs em elementos,
  fazer join, contar por elemento eficientemente, ou a lista crescer sem limite.
  Arrays são conveniência, não substituto para uma relação.

## Rede, binário, geométrico, range, especiais

- **`inet` / `cidr`** — endereços/redes IP; validam e ordenam corretamente, fazem
  matemática de subnet. Use em vez de `text`. **`macaddr`/`macaddr8`** para MACs.
- **`bytea`** — dados binários. Ok para blobs pequenos (thumbnails, chaves). Para
  arquivos grandes, armazene-os em object storage (S3/GCS) e mantenha uma coluna
  `text` de key/URL — não inche a tabela e o WAL com megabytes por linha.
- **`tsvector`/`tsquery`** — busca full-text.
- **Tipos range** (`int4range`, `tstzrange`, `daterange`) com **exclusion
  constraints** previnem overlaps de forma elegante (reservar uma sala para
  intervalos que se sobrepõem) — uma jogada sênior que a maioria não faz.
- **PostGIS `geometry`/`geography`** — trabalho geoespacial de verdade; não finja
  com duas colunas `float` se você precisa de queries de distância/containment.
- **`bit`/`bit varying`** — bit strings; nicho.

## Cola de tamanhos de armazenamento

| Tipo              | Bytes | Nota |
|-------------------|-------|------|
| `smallint`        | 2     | ±32.767 |
| `integer`         | 4     | ±2.1B |
| `bigint`          | 8     | default para PKs |
| `numeric`         | var   | exato, matemática em software |
| `real`            | 4     | ~6 dígitos significativos |
| `double precision`| 8     | ~15 dígitos significativos |
| `boolean`         | 1     | |
| `uuid`            | 16    | vs 8 para bigint |
| `date`            | 4     | |
| `timestamptz`     | 8     | sempre em vez de `timestamp` |
| `text`/`varchar`  | var   | +1–4 bytes de header de tamanho; perf idêntica |
| `char(n)`         | var   | preenchido com espaços — evite |
| `jsonb`           | var   | binário, indexável |

Tipos mais estreitos → mais linhas por página de 8KB → menos I/Os em scans. Real,
mas nunca ao custo de correção. Ordene colunas para minimizar padding de alinhamento
apenas quando a largura da linha genuinamente importar (tabelas muito largas, muito
grandes).
